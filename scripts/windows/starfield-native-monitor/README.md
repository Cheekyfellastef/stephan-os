# Starfield native monitor in the existing splash

The existing **Hybrid / Stephanos VR** card owns the next attended development
test from the saved independent bridge handoff. It displays a monitor-test
label. A headset playtest is a later milestone.

The operator opens the usual Starfield VR shortcut and uses that third card.
The splash shows preparation, the actual save-loaded confirmation, progress,
cleanup and the recorded result. No separate launcher or command prompt is
part of this route. Opening the splash or synchronizing source does not start
the experiment.

## Reused experiment

The native DLL, original loader, code manifest, archive and all 262 saved
members remain in the original November 5 workspace. The runtime verifies the
November 6 handoff and those exact artifacts before the experiment. This
integration does not rebuild or replace them.

The Python controller, setup/cleanup helper and evidence analyzer are reused
from the reviewed monitor package. The repository copies derive the original
fixed workspace from the current Windows profile, and the controller's public
Tk entry is replaced by the splash adapter. Their original prepared package
remains unchanged. The analyzer is copied without behavioral changes.

The adapter uses private redirected standard input/output for one owned child.
Its closed protocol carries only the fixed monitor actions and bounded status.
It exposes no network listener or arbitrary command, script or file operation.
The splash grants foreground permission to that exact child only when the
operator confirms that the save is loaded.

## State and evidence

The same one-attempt journal is retained under the saved workspace's outputs.
Changing the entry surface does not create a fresh attempt, consume an old
save-loaded confirmation, clear a lock or overwrite an existing capture.
Process identity includes the exact decimal creation FileTime as well as PID.

The reviewed probe runs at most once after fresh confirmation, loaded-scene
checks, current process checks and original artifact validation. Cancellation
uses the existing normal-close/restore path. An uncertain child, changed file,
missing receipt or incomplete cleanup remains visible and cannot be converted
into successful capture evidence.

One splash owns the provider controls until its dispatched children have
settled. Reopening the splash checks the existing monitor journals, locks and
restore receipt before releasing those controls. Completed monitor cleanup
does not prevent a later normal VorpX or MutaR provider selection.

The result distinguishes typed native-output analysis, process identity,
normal exit, proxy restoration and evidence integrity. A generic terminal
record or a loaded module is insufficient. Even a successful monitor result
keeps `playableVRProven` false: the current experiment does not deliver native
game images to the headset.

## Delivery and review

The existing canonical main synchronization adopts these source files for the
next explicit splash invocation. Exact paths are classified as natural reload;
Python fixtures are classified as non-runtime. Unknown neighboring scripts
remain unclassified. Exact `.gitattributes` entries keep the hashed Python
bytes stable on Windows checkouts with automatic line-ending conversion.

Validation must cover the adapter, original controller regressions, setup and
analysis fixtures, splash bootstrap/protocol, preserved provider routes and
post-sync classification. Independent source review is separate from the
authenticated protected-merge review and from an actual Windows run. None of
these is a substitute for either of the others.
