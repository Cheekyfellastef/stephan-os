# Anti-Native Doctrine

In Stephanos terms, “going native” means introducing local one-off behavior that bypasses canonical truth models, shared projections, and protected surfaces.

## Bad (do not do)
- Local state replacing canonical projections.
- One-off pane/copy/route implementations outside existing canon.
- Direct DOM/CSS hacks without canonical surface alignment.
- Duplicate Mission Console surfaces or duplicate answer panes.
- Direct provider-truth shortcuts that collapse distinct truth stages.
- Isolated telemetry/status walls detached from shared truth engines.
- New systems that do not connect to Mission Brain, Support Snapshot, or Ignition.

## Good (do this)
- Use canonical projections and adjudicated truth outputs.
- Extend existing truth models rather than replacing them.
- Reuse shared UI primitives and protected interaction patterns.
- Add targeted tests/guards for risky or repeated failure areas.
- Add Support Snapshot/browser-proof evidence for UI-facing claims.
- Improve ignition/housekeeping where the failure pattern indicates drift.

## Practical rule
If a fix works only in one local path and does not strengthen shared truth, it is probably native drift and should be redesigned.
