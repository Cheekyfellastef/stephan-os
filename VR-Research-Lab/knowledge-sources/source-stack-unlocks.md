# VR Source Stack Capability Unlocks

Status date: 2026-07-29

## Source stack

| Layer | Primary source | What it contributes |
|---|---|---|
| Normative contract | Khronos OpenXR-Docs | Required lifecycle, spaces, views, actions, composition and extension semantics |
| Reference implementation | Khronos OpenXR-SDK-Source | Loader, API-layer and minimal application implementation evidence |
| Universal Unreal conversion | UEVR | Broad injection, stereo, camera, UI and profile patterns across UE4/UE5 |
| Shared engine framework | REFramework | Common native runtime with scripting, plugins and per-title adapters |
| Commercial profile driver | vorpX | DirectVR automation, profile inheritance, geometry/depth stereo and fallback presentation modes |
| Alternate-eye multi-title framework | Luke Ross R.E.A.L. VR | Common injector, per-game modules, AER iteration and seated AAA conversion |
| Open title-family implementation | Mutar / NoMoreFlat | Starfield and Anvil-engine source, 6DoF, HUD, controller translation and OpenXR/OpenVR variants |
| Native multi-title case study | Halo MCC VR | Reverse engineering, capability ownership, exact-hash headset proof and AI-assisted delivery |
| Native interaction benchmark | Skyrim VR ecosystem | Body IK, calibration, gestures, holsters, grabbing, collision, two-handing, physics and character kinetics |
| Performance specialisation | Quad-Views-Foveated | API-layer foveation, quad views, compatibility gating and performance budgeting |

## What the combined stack unlocks

### 1. A comparative architecture engine

Stephanos can compare the same problem across:

- normative specification;
- authoritative reference implementation;
- universal engine injection;
- shared engine frameworks;
- commercial profile-driven conversion;
- alternate-eye multi-game conversion;
- open title-specific and engine-family adapters;
- native VR interaction layers;
- specialised performance API layers.

This makes it possible to distinguish a reusable principle, a renderer-family technique, a title adapter, an interaction layer and a local workaround.

### 2. A conversion-strategy selector

For a target game, the Capability Graph can evaluate:

- native engine stereo;
- geometry stereo;
- synchronized sequential or alternate-eye rendering;
- depth-derived stereo;
- title-specific camera and render hooks;
- a shared engine adapter;
- OpenXR API-layer intervention;
- immersive-screen fallback;
- or a bounded hybrid.

The recommendation must include evidence, compatibility, licence, comfort and proof requirements.

### 3. A measurable Skyrim-parity rubric

Skyrim VR parity can now be decomposed into provider-owned capabilities rather than used as a vague slogan:

- base-game stereo, tracked input and world support;
- SKSE extension and plugin loading;
- VRIK body, calibration, gestures and holsters;
- HIGGS grabbing, collision, two-handing, object physics and interaction APIs;
- PLANCK character kinetics and physical combat response.

Each Starfield slice can name the exact benchmark, required evidence and fallback behaviour.

### 4. Layer-responsibility diagnosis

Failures can be classified by likely ownership:

- game or engine;
- graphics-API hook or injector;
- common framework;
- title adapter or profile;
- body/interaction/physics mod;
- OpenXR application;
- API layer;
- loader;
- runtime;
- headset or transport;
- configuration or performance envelope.

This reduces random experimentation and improves the information value of every headset test.

### 5. Reusable capability and lifecycle modelling

The combined evidence supports structured models for:

- loaded versus active runtime ownership;
- lifecycle generation and freshness;
- session and frame legality;
- independently gated stereo, tracking, input, HUD, body, IK, physics and haptics;
- calibration and seated/standing state;
- teardown and handoff;
- disconnect and restart;
- explicit unsupported and unknown states.

### 6. Evidence-led embodied validation

The proof ladder is now:

1. normative validity;
2. source, profile or architecture evidence;
3. deterministic desk tests;
4. packaged candidate identity;
5. exact versions, hashes, configuration and mod stack;
6. physical headset result;
7. regression across previously accepted targets;
8. accepted-state pointer and rollback route.

### 7. A stronger Method Library seed

Reusable methods now include:

- accepted-state pointers;
- per-target evidence isolation;
- generic-core plus bounded-adapter architecture;
- profile-first compatibility triage;
- explicit render-strategy fallback ladders;
- alternate-eye stability testing;
- capability negotiation rather than optimistic assumptions;
- transient-frame fail-soft behaviour;
- exact-hash and exact-mod-stack headset acceptance;
- calibration-before-polish;
- physical-interaction fallbacks;
- frame-rate-aware physics;
- compatibility matrices across app, graphics API, framework, runtime and headset;
- licence-aware source ingestion and legal-availability tracking.

### 8. Starfield VR programme acceleration

The programme can now compare:

- Mutar's direct Starfield implementation;
- REFramework's common foundation;
- Luke Ross and vorpX as alternative seated conversion strategies;
- Skyrim VR as the interaction and extensibility benchmark;
- OpenXR sources as the correctness baseline;
- Halo MCC VR as the lifecycle and proof benchmark;
- Quad Views as an optional performance layer.

This allows the next Starfield goals to target the largest evidence-backed parity gap rather than rebuilding solved foundations.

### 9. Professional Spatial Bridge preparation

The future Quest bridge can draw separately from:

- Khronos for OpenXR correctness;
- reference samples for minimal client structure;
- UEVR, REFramework and Mutar for extension and configuration patterns;
- vorpX and Luke Ross for seated presentation and compatibility methods;
- Skyrim VR for calibration, spatial interaction, menus and fallback design;
- Halo MCC VR for lifecycle, proof and multi-module ownership discipline;
- Quad-Views-Foveated for later performance optimisation.

The first bridge slice remains a thin, read-only client over canonical Stephanos state. Game-mod injection patterns must never be mistaken for authority architecture.

### 10. Autonomous research work

Once #1596 and the Mission Scheduler are live, workers can:

- compare upstream revisions, public versions and releases against pinned snapshots;
- create material-change candidates;
- refresh compatibility, availability and licence state;
- extract evidence-linked graph records;
- compare alternative conversion strategies;
- maintain the Skyrim parity matrix;
- propose high-information experiments;
- update Method Library candidates;
- return completion receipts without an open chat.

## Current gaps

The expanded stack is sufficient for serious comparative extraction and Starfield parity planning. Later evidence may still be useful for:

- a full open-source OpenXR runtime and compositor;
- OpenVR-to-OpenXR translation;
- standalone Quest-native rendering and transport;
- WebXR thin-client presentation;
- accessibility and comfort telemetry;
- long-duration headset reliability.

These remain discovery candidates, not automatic additions. New sources must fill a distinct gap and pass provenance, licence, freshness and distinct-value checks before registration.
